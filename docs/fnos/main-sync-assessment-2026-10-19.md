# main → fnOS 选择性同步评估

初评日期：2026-10-19；2026-10-20 补核 main 增量与目标设备验收。成本是基于代码和依赖边界的相对评估，不是工期承诺。

本轮范围已扩展为五项低成本回迁、SDK 0.15.0、显式 JEV 配置和检索，以及资源生命周期修复。采用选择性适配，保留 fnOS 原有数据目录、处理流水线和 Native FPK 交付边界。

## 验证与边界

每项改动均先取得失败回归，再验证修复。旧五项回迁曾通过完整自动化；这些历史数量不作为 SDK/JEV 最终交付的验收结果。

新增回归包括真实 0.13 两租户 SQLite/Lance 数据、SDK 0.15 原生事件到分块的评分、HTTP scorer 的鉴权/完整 URL/模型、401/503/超时与显式粗排策略、权限范围出站前过滤、评分期间逻辑删除、配置热更新，以及连续取消时真实 FD 的释放。无事件的向量候选与已评分候选分别计数，页面不把未调用 scorer 的结果标成 JEV 完成。

自动化已完成：macOS 后端在末轮预算修复时为 922 passed / 2 skipped，前端 548 项通过；i18n、类型检查、ESLint 和 `/app/sag` 生产构建通过。Linux 原生完整后端在 `8642c8dd` 为 924 passed / 1 skipped，仅跳过未启用的专用 PostgreSQL E2E。其后 `4a6c4437` 仅调整关闭时第二次发放 worker lease 前的检查顺序并新增确定性并发回归，macOS 与原生 Linux 的相邻五文件分别 84 项通过；不将前一版本的全套数字冒称后一版本的完整重跑。最新向导与真实 fnpack 合约回归为 160 passed / 2 skipped。跳过项涉及平台能力、独立 PostgreSQL E2E 或由另一平台覆盖的 fnpack 合约，不能作为对应环境已通过的证明。

以下覆盖与全新安装的完整设备功能验收基于 `73ec48ac` 候选。目标 x86_64 设备已实际完成官方 1.5.11 手动安装基线到候选 1.5.12 的覆盖升级，136 个生产 Python 文件与候选源码逐一匹配，安装依赖为 SDK 0.15.0。原有知识的 2 文档 / 65 分块 / 202 事件、模型配置和会话保留；旧 PDF 正文读取、默认 vector 检索，以及新上传 PDF / 数值 Excel 的实际解析、抽取和入库均通过。MCP 能读取 PDF / Excel 的解析正文并检索数值，临时测试授权已撤销。

覆盖和全新安装均验证了 104,222 字节长 Markdown：原始文件模式的 362 个文本块拼接后与上传文件逐字一致，解析内容模式也与解析 API 的 104,245 字节返回值逐字一致，两者均核对全文 SHA-256 和首尾哨兵。解析结果与上传串之间的 23 字符差异单独保留：SDK 0.13 和 0.15 均对块内容 `.strip()` 后以双换行拼接，不能把两种表示混作同一个字节保真契约。

两种安装场景均完成独立 JEV 连接探测、保存后仍为 vector、显式启用，以及 REST/SSE/compare/Agent 的真实评分。使用原生 ranking 统计和证据 metadata 判定实际评分，界面区分已评分与未评分向量候选；问答返回正确采购数值和引用。MCP 阅读、检索文本事实及临时授权撤销通过，但 MCP 不返回 ranking stats，不能据此单独证明其原生评分次数。

全新安装首次启动为零信源、四类服务 Key 均未配置，旧信源不可访问；通过正常配置接口设置测试模型后，PDF、Excel 和 NAS Markdown 均达到 ready。第二个真实 fnOS 会话验证了独立空库、空检索、跨租户信源拒绝、无 Key 继承及独立 JEV 草稿持久化；修改第二账号预算/失败策略未改动第一账号配置。第二账号没有有效服务 Key，未声称两个账号都执行了外部 JEV 正向评分；两租户正向存储隔离另由真实 SDK fixture 回归覆盖。

目标设备实际走 `legacy_manual` NAS 授权路径：仅新增合成目录只读授权，完成扫描、复制入库、变化文件保留 ID 更新、运行中 `extracting → pausing → paused → extracting → ready`、删除及 stop/start。删除后的详情/file/preview/parsed 均为 404，检索不再返回旧/新测试事实。宿主撤权会自动停用应用，重新启用后扫描为 `422 nas_folder_unreadable`，旧 token 为 `409 nas_selection_expired`；先前私有副本仍可读取，符合一次性复制合同。该路径证明撤权与重启后的拒绝访问，不证明同一 worker 内复制阶段的 ACL 检查；自动共享 API 路径及评分出站内容检查由独立回归覆盖，不冒充真机证据。首次以进度阈值捕获暂停阶段未成功的记录保留，后续使用明确的 extracting 状态才完成暂停恢复；不声称真机验证了已有完成分块的断点恢复。合成信源、目录与新增宿主权限已清理。

真实 fnOS iframe 在 390 像素外层视口、324 像素内容宽度下验证了会话、移动导航与 JEV 表单，文档宽度与 scrollWidth 均为 324；另验证新建会话跨知识库导航后仍保持草稿。此为桌面浏览器响应式模拟，未使用实体手机。

同一设备以包用户和普通用户分别在独立目录执行初始化、真实资源、取消、应用停止、JEV 和真实 0.13 fixture 等十个文件，各 113 项通过；原生 LanceDB 打开/关闭也通过。另在普通用户同一 pytest 进程执行六种真实资源场景各 20 轮，共 120 次执行，所有轮后 FD 均为 23，目标映射也一致，稳定段增量和斜率均为零。业务关闭断言在防御性 fixture 回收前完成；轮后采样在 function fixture 回收后完成。此为约一分钟的有限隔离负载，不代表 FD 归零或生产包用户的长期资源趋势，生产进程 FD 枚举权限不足的边界保留。实际 Python 进程 nofile soft 为 4096。Linux x86 仿真环境仍有最小 LanceDB 打开时的崩溃，另一个 ARM 测试环境出现过 JEV 预算超时；不能将这些环境记录为全绿，也不能仅凭目标设备通过断定仿真崩溃原因。

设备冷备已完成归档哈希、逐文件和 SQLite 完整性校验。两种安装场景后从原归档重新解出数据，校验所有文件内容和属主后原子恢复；启动后的 API 和页面确认原 2 文档 / 65 分块 / 202 事件、4 个会话、模型配置及默认 vector 恢复，测试 JEV Key 不残留。原冷备及隔离副本继续保留。Linux 原生全套与此前十文件的 113 项回归分别记录。全套首轮因隔离运行模板额外覆盖认证、内部 socket/secret 配置及缺少模板执行位而出现 31 个失败/错误；保留原始失败，恢复仓库默认配置、tracked 权限并使用新建隔离数据库后，完整执行为 924 passed / 1 skipped，未修改原测试断言。
