# 引用规范

## 为什么需要引用

SAG 是原文溯源型知识库——每条检索结果都能追溯到原始文档的具体分块。引用规范保证：
- 用户能验证答案的准确性
- 追问时能快速定位原文
- Agent 回答有据可查，避免幻觉

---

## 引用标注格式

使用 search 返回的 `[n]` 编号标注每条外部知识来源。

```
search 返回:
[1] 授权流程概述（chunk_id=chunk_042）
授权分为三步：……

[2] 权限模型（chunk_id=chunk_078）
系统采用 RBAC 模型……

Agent 回答:
授权分为三步：用户发起、主管审批、系统记录 [1]。
权限控制基于 RBAC 模型，支持角色、用户组、资源三级粒度 [2]。
```

### 标注位置

- 标注紧跟被引用的句子或段落末尾。
- 一句话引用多个来源时并排标注：`[1][3]`。
- 不要把所有引用堆在段落末尾——逐句标注。

### 标注粒度

- 每条来自知识库的事实都要标注。
- 常识性内容（如"RBAC 是 Role-Based Access Control 的缩写"这类通用知识）不需要标注。
- 不确定是否需要标注时，倾向于标注。

---

## 原文溯源流程

当用户追问出处时，按以下步骤展示原文：

```
用户: 这个授权流程是从哪来的？

Agent:
1. 确认引用编号 → 上一轮回答引用了 [1]
2. get_chunk(chunk_id=chunk_042) → 获取完整分块原文
3. 展示原文并说明来源文档

回复示例:
这来自《产品手册》第 2 章「授权流程概述」：

> 授权分为三步：用户发起请求，主管在线审批，
> 系统自动记录并通知。请求需在 24 小时内完成审批，
> 超时自动退回。
```

---

## 追问处理模式

| 追问类型 | 处理方式 |
|---|---|
| "这个结论从哪来的" | get_chunk 展示对应原文 |
| "原文怎么说的" | get_chunk 展示对应原文 |
| "有没有更详细的内容" | read 相关章节（先 outline 定位） |
| "还有其他相关的内容吗" | 扩大 search top_k 或换表述再 search |
| "这个人在知识库里还有什么信息" | get_entity 查看实体上下文 |

---

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 回答中不标注任何引用 | 每条知识库事实必须标注 `[n]` |
| 标注了 [n] 但 n 是编造的 | [n] 必须来自当次 search 的真实返回 |
| 用户追问出处时复述而非展示原文 | 用 get_chunk 展示原文 |
| 把常识当作知识库内容标注 | 只有来自 SAG 的知识需要标注 |
